# Fields, computed fields and automations

The Gateway reads typed values (a sensor's temperature, a frame of bytes), derives new ones from them, and tells the assistant when one becomes a value the owner named. None of it reaches the phone as code: the phone reads the declarations and the values.

## The field table

`src/shared/field-types.ts` holds the kinds and their rules once; codegen writes the same data into `Protocol.kt` as `FieldTypes`, and `kotlin-gate.sh` diffs it.

- **Kinds:** `enumeration` (Choice), `text`, `number`, `bytes`. Choice takes `is` and `is_not`, text those and `contains` and `contains_not`; number and bytes take none, and `conditionsIssue` refuses a condition over them. `TEST_LABELS` reads a test with one value and `LIST_TEST_LABELS` with several ("is any of", "contains none of").
- **Units:** a number is stored in a stored unit (`C`, `%`); `F` is a display unit only. `toDisplay` and `fromDisplay` convert, a converted value storing at 0.01 so it reads back as typed.
- **Range:** `inRange` keeps `|value| x 10^decimals` within 2^53, so both runtimes format it the same.
- **Bytes:** lower-case hex, at most 64 bytes, shown as offset rows of eight (`bytesText`).
- **Parse and render:** `parseFieldValue` in `src/shared/field-values.ts` answers a value or an issue (`path`, `message`, `code`), rounding a reading to its declared decimals. `formatFieldValue` is the one text renderer; `FieldRules.kt` is its phone twin.
- **Pinned:** `tests/fixtures/field-types/vectors.json` (grammar, rounding, conversion, range, rendering), replayed by both runtimes.

## Owner records

`src/gateway/ownerRecords.ts`, `createOwnerRecords`: the store under computed fields and automations. Phone-minted ids, Gateway-named revisions, buried ids, `commitChecked`, `onChanged` after the write. `batch` plans several puts and removes against one draft and lands them in one write, or none when any is refused. The envelope (`id`, `revision`, `incarnation`, `kind`) parses strictly; a body this build cannot read is held unread, reserves its id and its place in the cap, and is written back untouched. A put carries its base revision, and a repeat of the stored content answers stored. The `refusal` hook runs on every put and on `invalidOf`, so validity is read, never stored; a refusal may carry the issue shape. A put marked `unfit` lands past it, for a record that arrives with the assistant. `refusalOf` plans a batch and answers its refusal without writing. A refusal carries an `OwnerCause` (`bad_id`, `invalid`, `newer_build`, `moved`, `spent`, `absent`, `removed`, `unsaved`, or a `cap` naming the total or a kind), so no caller guesses a code from prose, and `batch` checks `maxByKind` and the total against the batch's final row count, whatever order it lists its writes in. `unreadOf` says whether a newer build's row holds an id.

## Expressions

`src/shared/expressions.ts`. A flat node table, each node naming only earlier nodes: field, literal, compare, all, any, not, choose, band, take, arithmetic, unknown. At most 64 nodes.

- **Check:** `checkExpression` types every node against the inputs' declarations and refuses with an issue naming the node. All-text-literal branches infer a Choice of those literals.
- **Evaluate:** `evaluate` never throws. Whole-number arithmetic runs on BigInt and truncates toward zero; a result past 2^53, a division by zero or a short frame answers unknown. A band keeps its side, by node index, until a value passes its dead zone.
- **Values:** known or unknown with a reason. `conforms` reads a known value off its declared type as unknown.

## Computed fields

`src/gateway/computed/computedFields.ts`, `createComputedFields`. A computed field is a label, an optional unit and decimals, and a node table. Fields may name fields, as a DAG at most `COMPUTED_DEPTH_MAX` (256) deep, and at most `COMPUTED_FIELDS_MAX` (256) exist.

- **One input port:** `input(ref)` answers a field's declaration and value together. Each pass reads every input once and resolves one snapshot of types, order and validity, which `typeOf`, `invalidOf` and `value` read.
- **State:** per field, a basis hash (expression plus every input's type), an `epoch` minted per fresh baseline, the last known value, `seq`, the band sides and the last 16 transitions (`previous`, `value`, `at`), all in one commit. An expression edit or a type change starts a new epoch and tells nothing; the first known value is a baseline. An unknown result reads unknown and keeps the last known value for the next comparison.
- **Calls:** `start()` runs the first pass once listeners are wired; `inputsChanged(keys)` re-evaluates fields naming those keys and their dependents; `typesChanged()` re-evaluates everything. `onCommit` fires after every landed write.

## Automations

`src/gateway/computed/automations.ts`, `createAutomations`, over the record in `src/shared/schemasAutomation.ts`. An automation is `enabled`, a trigger, a list of actions, an optional `label` that replaces the row's sentence, and optional `keepTryingMin`, the retry window each step gets (ten minutes when absent). A trigger is `event` (a source and its conditions, decided in the assistant's lane), `value` (a Choice or boolean computed field and the value it `becomes`), `crossing` (a sensor's number, with device, measure, direction, threshold and dead zone), `time` (a local time on its weekdays in a recorded zone) or `interval` (everyMin, counted from its last handled slot). `coolDownSec` belongs to the trigger: optional for event, required for value and crossing, absent for time and interval. Event cool-down is counted from its last admitted match, during which it neither runs nor wakes the assistant (`docs/assistant.md`). An automation holds one to `AUTOMATION_ACTIONS_MAX` (256) actions, each a row of `AUTOMATION_ACTIONS` in `schemasAutomation.ts`: `tell_assistant` with `when` `now` or `quietly` and an optional `message`, `device_set` (a switch this Gateway holds and a verb) and `ifttt_trigger` (an event and up to three values). A threshold on a sensor is a `crossing` the owner writes.

- **The action catalogue:** a row is the action's label, where it runs, `danger`, `home` (away from the assistant's home it is refused unsent and an editor does not offer it) and its `params` in the order an editor draws them. A parameter is a name, a label and a kind: `text` (prose that may hold holes, with a `max`), `word` (letters, digits, `-` and `_`), `switch` (one of this Gateway's switches) or `choice` (one of its `options`). `automation-actions.test.ts` holds each row to its action's schema, and `holeTexts` finds an action's texts by its row. The listing serves the rows whole in `serves.actions`, so an editor draws an action from what its Gateway says and needs no build of its own for a new kind.
- **The trigger catalogue:** `AUTOMATION_TRIGGERS` holds one row per trigger kind with the names a text's hole may use and a short description of each (`event` and `source` for an event; `value`, `device`, `measure` and `threshold` for a crossing; `time` for a clock). `AUTOMATION_TRIGGER_NAMES` is derived from it, so the save's hole check, the fill and the preview read one table, and a test holds each row's names to what a real fire fills. The listing serves the rows in `serves.triggers`, so an editor lists a trigger's names before the trigger is complete.
- **Functions:** a function is an owner record beside the automations (`src/shared/schemasFunction.ts`): a name, up to `FUNCTION_PARAMS_MAX` values typed `device`, `text` or `number`, and a tree of steps. A `do` step runs an action, its arguments literals or expressions read at the step's start. At most `FUNCTIONS_MAX` (256) exist beside `AUTOMATIONS_MAX` (256) automations, the total being their sum, one id space spans both kinds, and a function a newer build wrote is held unread, counted in the caps, and its automation reads `FUNCTION_UNREAD` and never fires. An automation runs one through the `run_function` pointer (`function`, literal `values`), which is never an effect and so has no runner; `FUNCTION_STEP_KINDS` is held against the action kinds and validity's step table is built from it.
- **The tree:** a step is `do`, `if` (`when`, `steps`, `else`), `switch` (`subject`, `cases` each holding `values` and `steps`, `default`), `try` (`steps`, `catch`), `parallel` (`steps`, each run beside the others), `exit`, `throw` (`text`), `let` (`name`, `value`), `wait` (`minutes`), `note` or `call`. A list holds at most `FUNCTION_STEPS_MAX` steps, a body `FUNCTION_STEPS_TOTAL_MAX` in all, nested `FUNCTION_DEPTH_MAX` deep. A switch holds at most `SWITCH_CASES_MAX` cases, each at most `SWITCH_CASE_VALUES_MAX` values.
  - **A step's path** is numbers alone, owned by `automation-walk.ts`: `0.2.0.1` is the call at action 0, its step 2, that step's first side, step 1. A first side (an if's then, a try's body) is 0, the second (else, catch) is 1. A switch's case is its own number and its default is past the last (`case:N` in an address). `sidesOf` and `withSides` are the one reader and writer of a step's lists on each runtime.
  - **How a frame moves:** `moved` in `automationFrames.ts`, pinned by `tests/fixtures/automation-frames/failure-table.json`: a failed step is remembered and the next runs; inside a try it jumps to the catch with the failure as `e`; a `throw` unwinds to the nearest try or ends the frame; `exit` adds no failure and keeps any earlier uncaught one. A frame that ends with a failure nothing caught ends its call refused.
  - **At its turn** an `if` takes the side its condition holds and fails `unread`, taking neither, when the condition is not true or false. A `switch` reads its subject once as the text a hole holding it prints, and takes the first case holding a value equal to it under `caseKey` (`src/shared/switch-cases.ts`: trimmed, lower case), else its default; a subject that cannot be read fails `unread` (`SUBJECT_UNREAD`), taking no case. No case falls through. The step and the last run keep the case taken as `case`, the default being past the last. A `let` keeps a JSON value in the frame's `vars` (`FRAME_VARS_MAX` of them, each within `FRAME_VAR_BYTES_MAX` bytes). A `wait` stores when it ends and the run goes on at the first pass after it, a restart included; a waiting run is started, so no newer fire evicts it.
  - **Tasks:** `start` (`steps`, `as`) runs its steps beside the steps that follow and keeps a task under `as`; `await` (`task`, an expression, and `as`) waits for the task, `all(a, b)` or `any(a, b)` it reads; `all` and `any` take joins too, so `any(all(a, b), timer)` waits for both or the timer. A task reads `done`, `failed` and `error` as the run stands, and prints `running`, `done` or `failed` in a hole. `await t` ends as `t` did; `await all(...)` waits for every task and fails `together` with each failure; `await any(...)` ends with the first to end, though several ended before it asked, keeps that task under `as` and never fails. A failure follows the ordinary rule where the await sits, so a `try` catches it. An await that names no task of this run fails `unread`, and one that would wait on itself, directly or through another await, fails `refused`. Nothing is left behind: a function does not end, at its last step or at `exit`, while a task it started still runs, and a failed task no await of one task or of `all` took fails the call then. `exit` inside a task is an error, as inside a block. In script: `t = start { ... }`, `t = start` and any one statement (a block of one, `timer = start wait(5)` included), `await t`, `first = await any(a, b)`. Cards draw neither, and keep one as they keep any step they cannot draw.
  - **Side by side:** a `parallel` step opens a strand on each of its steps and ends when every one has: done, or failed `together` with `errors`, each failed branch's first failure nothing in it caught. That failure follows the ordinary rule where the block sits, so a `try` around it reads `e.errors`. A strand ends at its root: a `try` guards only what is inside its own strand, a `throw` ends its strand alone, and an `exit` written inside one is an error. A run holds at most `RUN_STRANDS_MAX` (256) steps whose turn it is; a wider body is an error, and a block that would pass the cap through a call ends refused at its turn. Up to `EFFECTS_MAX` (4) attempts are out at once across every run, one to a device, and one run's steps on a device go in the order written. In script it is `parallel { ... }`, one branch to a line.
  - **Scope** for a step: the trigger's names, the function's values, the frame's variables, and `e` inside a catch (`code`, `message`, printing its message).
  - **A set after a wait** is dated by the wait's end (`intentAt`), so it does not lose to another automation's set that landed while it waited.
  - **Step checks** are one entry per kind in validity's `STEPS`, read at every depth through `stepsOf`. An issue names its step by those numbers in `step`, with `param` and, for a hole, `start` and `end`. A blank condition or value parses and is an error.
  - **A switch's issues** are `switchIssues` in `switch-cases.ts`, pinned by `tests/fixtures/switch-cases/vectors.json`: a case with no values, and a value equal under `caseKey` to one before it, are errors (`STEPS.switch`, after the subject's expression check). A value its choice field no longer holds is a warning, and that case simply never matches it: `assessBody` yields it where the trigger is known, and a choice subject is exactly `event.<field>` naming an `enumeration` spec of the trigger's source (`choiceFieldOf`). A case issue carries `case` and `value`. A choice field's options never differ only by case. The phone's twin is `assistant/SwitchCases.kt` (`caseKey`, `choiceFieldOf` read from `lexConsole` tokens, `switchIssues`), replaying the same vectors in `SwitchCasesVectorsTest`; the cards draw a switch from it (`docs/assistant.md`, the editor), and the phone caps cases and values by the generated `SWITCH_CASES_MAX` and `SWITCH_CASE_VALUES_MAX`.
  - **A step with errors** saves, and its run fails it at its turn: `errorAt` reruns the step's check on the body the frame pinned, and an error ends the step `unread` with the fixed `STEP_ERRORS`, after the steps before it ran. A `try` catches it as any failure; else the frame ends failed and its call `call_failed`. A flat action is checked the same way.
- **The script:** a function's steps are also a text, printed and parsed by the Gateway alone (`src/gateway/computed/automationScript.ts`). The phone holds no parser.
  - **The text:** one statement to a line, blocks in braces, tabs for indent, `start` and `await` as above. `// text` is a `note` (lines that follow one another are one note, a blank line parts two, and a comment after a statement is a note before it), `name = value` a `let`, `if (when) { } else if (when) { } else { }` an `if`, `switch (subject) { case "a", "b" { } default { } }` a `switch` (its values quoted constants, a hole refused, `default` last), `try { } catch (e) { }` a `try`, then `exit`, `throw "text"`, `wait(minutes)`, `entity.method(values)` a `do` and `functions.run("Name", {name: value})` a `call`.
  - **A doing call** is named by its action's row (`call` in `AUTOMATION_ACTIONS`): `assistant.tell(when, message?)`, `devices.set(device, verb)`, `ifttt.trigger(event, value1?, value2?, value3?)`. Values are positional in the row's order; trailing optional ones are left off and one skipped in the middle is written `null`.
  - **A value** (`StepArg`) is a `literal`, as written, or an `expression`, kept as its own text. Only an action's text parameter fills a literal, where a literal has always been the text, so a value typed on a card or set by a pointer means what it says.
  - **A quoted string** is read by the one lexer wherever it stands (`docs/console-live.md`), and what it is depends on its place alone. In an action's text parameter and after `throw` its body is the text the step stores, holes and all. For a plug, a choice, a word and a function's name it is a constant, and a hole there is refused. In a `let` or a call's value it is a constant when it holds no hole and an expression when it does, so `label = "Room {device}"` keeps the expression `"Room {device}"`. A hole's own strings need no escaping: `"It is {if(cold, "brr", "ok")}"`. A literal brace is written `\{` in every quoted string.
  - **An expression stays an expression:** one that would read bare as something else prints in parentheses. That is one literal anywhere, `(5)`, a bare `null` where it would read as a value left out, `(null)`, and a string with a hole anywhere but a kept or given value, `("is {a}")`.
  - **Names for ids:** a plug or a function is written by its name when exactly one holds that name and no id is spelled so, else by its id. Reading takes an id first, then a name, and refuses two of a name and a function not held.
  - **The canonical function** is `parse(print(f))`: a text's lone backslash is doubled, an expression's line breaks become spaces (one for each character, so a span holds), an empty `if` side or switch default is absent. A constant is kept as it is, whatever it holds. A seeded sweep pins that every function settles after one round.
  - **What reads only:** a `do` naming no action, a `do` with `as`, a call to a function not held or giving a value it does not take, a `let` named as a word the language took (`switch`, `case` and `default` among them), a switch with a blank subject or a case with no values, a text with an open hole, and anything else whose printed text would not parse (a value that outgrows `STEP_TEXT_MAX` once escaped): the printer parses what it printed and says `readOnly` when that fails. A text past `SCRIPT_SOURCE_MAX` is not answered at all, only why.
  - **The grammar** (`src/shared/script-grammar.ts`): `parseScriptSource` reads the lexer's script tokens into statements whose values are expression nodes, and `parseScript` lowers that tree to steps with the Gateway's tables. A `{` is a block after `if (...)`, `else`, `switch (...)`, a case's values, `default`, `try`, `catch (e)` and `parallel`, on that line or the next, and a record where an expression stands. A statement ends with its line, a comment or its block's `}`, and runs past a line break only inside a bracket. A statement that faults raises one issue and the parser carries on at the next line, past a block that line opened. The script's tokens are a section of `tests/fixtures/live-console-tokens/vectors.json`.
  - **Two console reads:** `script_print` (steps, with the draft's trigger, values and functions) answers the text, `readOnly`, each step's span by its path (`statements`) and each name with its type and where it is offered (`names`). `script_parse` (a text with the same) answers the canonical steps, or up to eight issues with spans; with steps it also answers every issue of the steps on their own (a name, a hole, an action's values), each placed in the text with its `level`. What a save judges across records (a call's fit, a loop, a confirm) is `automation_check`'s. `place` asks where a later refusal's step and value sit, each offset held to the value and an escape answered whole. Both answer `types`, the members of `Error` and, under an event trigger, of `Event` with its source's declared fields. `serves.functions.script` says a Gateway holds both, and `console_describe` with `script` answers a script's vocabulary: what a host reads, with the doing members.
  - **Types** (`src/shared/script-types.ts`): `Text`, `Number`, `Truth`, `Time`, `Device`, `Event`, `Error`, `List`, `Record`, `Unknown`, or a label the registry declares. `typeOfNode` reads an expression without running it and answers `Unknown` where nothing declares a type. A kept name is offered from the end of its statement, `e` inside its catch, and a name kept again ends its earlier reach.
  - **A script with errors** is an `unparsed` step holding the text as typed, its function's only step (`UNPARSED_ALONE`). At its turn it fails `unread` with `SCRIPT_ERRORS` and nothing of it runs, so its call ends `call_failed`; the automation stays armed, and the step reads and reaches nothing. Print answers its text with no statements. Parse never answers one: the phone writes it when the last parse of exactly that text had issues.
  - **On the phone** (`assistant/ScriptDraft.kt`, `assistant/ScriptView.kt`): each tree, the automation's own or a callee's, is shown as Cards or Script. Script is the Gateway's print, read-only with the last run beside its lines (`scriptLines`), and Edit opens the full-screen text editor in its script mode. What is typed is the tree's script edit, parsed once typing settles; an answer lands only for its own text and context (`scriptCurrent`), steps replace the cards, with each issue listed in its level's colour and the first error marked (`markedIssue`), and only text that does not parse makes the cards one `unparsed` step. Save waits for the parse and asks once when a function newly holds errors (`errorsAsk`). A tree is swapped only through `swappedOwn` and `swappedCallee`, which take its script state from the new body and close a page into the old one.
- **Fit:** `src/shared/automation-fit.ts` says whether a trigger and a pointer's values fill what a function takes. `AUTOMATION_TRIGGER_GIVES` is the one table of what each trigger kind gives by name and type, `EVENT_GIVEN_FIELDS` (`id`, `title`, `url`) beside a source's declared fields is what an event gives, and the fire reads the same table. `triggerGiven`, `fitOf` and `functionReads` answer fit, hidden (another source's event) and the names still to set. A crossing's `device` is the sensor's name and gives text, so it never fills a device value. `tests/fixtures/automation-fit/vectors.json` is replayed by `assistant/FunctionFit.kt`.
- **The save op:** `automation_save` (`schemasAutomationSave.ts`) is a value op carrying the automation, its base, an optional function as `edit` (an id and base) or `copy` (a `from` and its base), and `confirmed`. The judge lands the automation and its function in one batch, answering what it holds as `issues` (`AutomationIssue`: `level`, `record`, `id`, `step`, `param`, the span and `line`), or refuses with a code from `AUTOMATION_SAVE_REFUSALS` and its facts (`moved`, `gone`, `full` with `max` and `kind`, `invalid`, `unknown_function`, `newer_function`, `loop`, `private`, `confirm` with labels, `no_key`, `no_free_id` and the rest), never by prose. Only what the store cannot hold or the judge cannot judge refuses. `functionBase` names the function revision shown by the editor. `saveOpOf` also sends the held function's base when flattening; `judgeAutomationWrite` checks it against that function's stored revision and refuses `moved` if it changed. `automation_check` carries the same payload, writes nothing, and answers `ready` with the `issues` a save would land with, or the refusal a save would get now, with the `reads` of the body it would run; it shares one assessment with the save (`assess`), so the two cannot disagree on the same rows, and it reserves nothing. A copy takes the id `copyIdOf` names, claimed by `claimDerived` so a rerun reaches it and nothing is written over; the key is in `automation-function-key`, never logged or answered. A refusal on a function record names its `id` only when the caller sent that id (the function as `edit`, or one in `called`; `sentFunctions`), so a copy's derived id is never answered. A new event-triggered automation that reaches more than a tell, and an edit that gives a function's users new reach, answer `confirm`. The phone draws each answered issue on the card its `step` names (`checkIssuesOf`) and blocks Save only on what it cannot write (`runsIssue`).
- **The walk:** `reached` in `automation-walk.ts` answers what an automation does in written order as closed entries: an `action` (never a call), a `step` of a function a call was followed into, or an `unfollowedCall` with its reason (`not-expanded` without a function lookup, `missing` when the function is not held). `visit` reads an entry and needs a handler for every case and step kind. An unfollowed call proves nothing about what it reaches, so the confirmation rule counts no reach for it. `within` encodes a path below a call, `siteAmong` finds the call above a path, `below` gives the path under that call, and `byPath` orders paths. The phone's twin answers the same entries, pinned by `tests/fixtures/automation-walk/vectors.json`.

- **One assessment of a body, one policy:** `argsIssue` checks an action's values, flat or a step's (a hole only in a text parameter, a device value against the offered switches, a choice against its options, literal values against the action's row). `assessBody` yields every issue in written order (`trigger`, `choice`, `action`, `step`, `call`, `fit`, `name`), and `levelOf` gives each one level:
  - **`refuses`:** the store cannot hold it or the judge cannot judge it: a loop, the call budget, a private function, a call to a function not held, a step this Gateway has no row for, and a script beside other steps. The judge and the store's `refusal` hook refuse these alone.
  - **`unarmed`:** it saves and reads `invalid`: a trigger that cannot fire (an unknown source, a test its field does not take, a blank condition value), `FUNCTION_LEFT`, `FUNCTION_UNREAD`, and a hole read while no hole reader is composed. `automationIssue` answers these and `refuses`, for `armed`, `retireOf` and the row's `invalid`.
  - **`error`:** it saves armed and a run fails at it: every other step check, a flat action's values, a hole, and fit (the pointer's at entry, a call's at its entry). The row's `errors` counts them, read every time.
  - **`warning`:** it saves and runs on: a value or a kept name that shadows an entity or a word of the language, and an event condition's choice its source no longer offers, which matches nothing (`choice`).
  - Frame entry checks fit, a private function, a function gone or unread and the loop, never the callee's steps. A step's read values pass the same check before its effect. `automation_put` and the list row answer an older phone as before.
- **The list answers functions:** `functions` holds an `AutomationFunctionRow` (id, revision, body, `users` the automations that point at it in list order, `callers` the functions that call it, `moves` when an automation that reaches it moves with the home, `reads`, `invalid`) built in `listing()` from one store read. A function is unlisted only when no automation reaches it (`reachOf`); `usersOf` answers unknown while an unread automation or function row is held, and the delete at none and the sweep read that. `serves.functions` states the cap, the actions a `do` step may name (`steps`), the step kinds it runs (`statements`, absent from a build that runs `do` alone), the value types, and whether it serves unnamed functions (`unnamed`).
- **A call's frames:** a fire that enters a function holds a `frames` record by call path with the function, incarnation and revision it pinned, and the body pinned in `functionVersions` by `frameKey` (`commit` is the one writer, `pinnedFunctions`). The call step is replaced by the function's steps under dotted paths (`enter`); a function gone or unread at entry ends the call refused (`FUNCTION_GONE`, `FUNCTION_UNREAD`), and each step reads its values once at its turn into `frame.resolved`, ending refused with `VALUE_UNREAD`, `STEP_UNFIT` or `FRAME_UNREAD` rather than throwing. A function's tell is a step told through the outbox under `stepMember`. `keepTryingMin` sets each step's window, including in a called function. `fire` starts an event cool-down at admission; `cooled` also records one when the lane tells alone. Value and crossing triggers cool down from the transition's time. Clock triggers have no cool-down.
- **Calls:** a step may be `call { function, values? }`, running another function and waiting for it. Its values are by the callee's value names, each a literal or an expression read in the caller's scope when the call's turn comes; the callee reads the trigger's names, those values and its own variables, and nothing else of its caller.
  - **The walk** follows a call into its function, each step under the call's path, so a function reached twice is at two paths. A call it does not follow says why: `loop` (its function is already above it), `missing`, or `budget` (past `WALK_ENTRIES_MAX` entries).
  - **The run** enters a frame at the call's own path, pinned as a pointer's frame is and holding the values the call gave (`frame.values`). The callee's end is the call step's end: done, or failed `call_failed`, caught by a caller's `try` like any failure. `enter` refuses a function already on the frames above (`loop`) and a run past `RUN_FRAMES_MAX` frames, and checks what the call gave against the callee's declared types before any of its steps run.
  - **The save** refuses a loop (`loop`) and a call to a function not held (`unknown_function`). A call that leaves a value unset or gives one of the wrong type, and a callee whose reads the trigger does not give, save as that call's error and fail it at entry. `automation_save` takes `called`, the functions the automation's calls reach, written in the same batch; each must be reached by the automation as the save leaves it. The phone sends only callees it edited that are still reached, each at the base it read (`sentCallees`), and reads every other function from its listed row (`functionSource`). Every automation that reaches a written function is checked for what it would newly do, and reads its own errors after.
  - **One frame cap:** the walk follows no call past `RUN_FRAMES_MAX` functions entered, so a save refuses a body a run could not finish; the run's own cap is for an edit behind a waiting run.
  - **Users** are the automations that point at a function and the functions that call it. A function no automation reaches is unlisted and swept after a week; a move carries every function its automations reach and maps each call to where its callee landed. At the destination an automation already there keeps the function it holds and nothing lands on it or on what it calls; only what an arriving automation needs is landed; and a pointer or call whose function did not come lands where nothing is held.
- **A function with no name** is one automation's own steps: the record a tree is stored as when the owner gave it no name. `unnamed(fn)` is an empty name, and a name of spaces is refused. At most one automation points at it and no function calls it; a save that would break that is refused `private`, and a state that breaks it (a move never refuses for fit) reads invalid, `FUNCTION_PRIVATE`, and never runs. Naming it makes it an ordinary function under the same id; clearing the name of a function something else points at or calls is refused, so it is copied first. A build that requires a name holds the record unread.
- **The retire rule:** `retireOf` decides in order: the automation gone or another incarnation; `enabled: false` (`SWITCHED_OFF`); no pinned body; a started run, which continues on the body and frame it pinned; an unstarted fire at another revision; then the automation's own issues, its function left to frame entry. An edit therefore retires only an unstarted fire, and a function's revision change never retires one. A newer set landed on a switch ends an older open set of it even inside a function that has not resolved yet, the newest landed set per switch held in `landedSets`.
- **The carry:** a move takes functions by value (`CarriedFunction`, chosen by `carriedFunctionsOf` in `automation-carry.ts`, vectors under `tests/fixtures/automation-carry`). At the destination `judgeCarry` gives a function its own id unless an automation holds it or a staying automation runs it, then `carryIdOf`, the same on a rerun; pointers follow, and one whose function did not come never binds to a stayer's. A move in place claims the function a held event automation here already runs at its own id (`inPlace`) and, when it is held, leaves it as it stands. A let-go deletes no function: one with no user is tracked in `unusedFunctions` and swept after `FUNCTION_UNUSED_KEEP_MS` on the persist tick through the `sweep` intent, never while an unread row is held. A carry from an older phone (`functions` null) lands a pointer unfit only when its function is not held at the destination, so a move back binds to the function the let-go kept.
- **Clocks:** `automationClock.ts` names a time or interval trigger's next slot, `nextOccurrence` for a time and plain minutes for an interval. The state holds each clock's last slot handled; a clock that is saved, edited or switched back on starts from that moment, so it never fires for a slot before it. `tick()` fires each slot that has come round, tells the slot's clock time as `time`, and logs slots more than five minutes late as one `uncertain` run without firing them. One timer waits for the nearest slot, armed from the `now` the walk used, and the Gateway's persist tick walks again in case a timer was lost. A stored slot more than five minutes ahead of the clock means the clock went back: that automation's walk starts again from now and passes over the one slot it had last handled (`skip`), logging one `suppressed` row when it does, so a step back of any size refires nothing. A row answers `nextRunAt`. Neither kind moves with the assistant's home.
- **Fires:** a trigger that fires records a fire in the same commit as its checkpoint or slot: the automation, its incarnation and revision, a member key, the trigger's names, the fields it tells, and one record per action keyed by step path, with each step whose turn it is in `active` (one, unless a block opened more). An event trigger's fire is recorded by the lane once the poll that saw the event has committed, once per member (`memberKey`), so later activity on a thread fires again. `pump` in `automations.ts` is the one reader, driven by the pure rules in `automationFires.ts` (`nextEffect`, `claim`, `admit`, `mayRun`, `outdatedSets`) and in `automationSteps.ts` (`dueAt`, `heard`, `recovered`, `retries`). The state also holds each automation body a held fire fired with, by `versionKey`, in `versions`, whose one writer is `commit`; `bodyOf` and `stepAt` answer every question about a step after the fire (its nature, the kind on its log row, the switch a landed set names, the runner and the tell's text), so an edit of the automation changes none of them. It retires a fire whose automation is gone, was edited or cannot run here; `settle` decides that (`retireOf`) before recovery and before answers land, so a retiring fire is never resumed or retried, its steps are judged with no nature, and a retiring fire ends every step it began with what is known: a claim ends `no_answer`, an open step with a last word ends with it (`endHeard`, through `timedOut`) and logs its row, a step that never heard one logs nothing, then one retire row covers the steps left unreached, none for a finished fire. Each effect (every action that is not a tell) is a step. A fire's steps run in written order, one effect in flight across every fire, each claimed in its own write before it runs (`runEffect` in `automationRunner.ts`, which never throws), and a failed step is logged and the next runs. An attempt answers `done`, `refused`, `unreachable` or `no_answer`, or is a hold, which is no attempt: nothing was sent (the vault cannot be read yet, the devices are not loaded, the device road did not start it by its deadline, or a throw before the send). A step ends logged with its action kind as `ran`, `refused` or `uncertain`. `attemptOf` in `automationActions.ts` maps the road's `Outcome` to a word (a driver failure through `FAILURE_WORDS`, a refusal as `refused`), and an effect the latch marks unknown is `no_answer`. `KIND_NATURES` and `VERB_NATURES` beside `RUNNERS` give each effect `sets` (on, off), `sends` (an IFTTT post) or `nudges` (a toggle), and `RETRIED` in `automationSteps.ts` is the one table of nature against word: `sets` retry `unreachable` and `no_answer`, `sends` retry `unreachable`, `nudges` retry nothing, and `refused` ends every nature. A step keeps trying for `KEEP_TRYING_MS` from its own turn, backing off `BACKOFF_MIN_MS` to `BACKOFF_MAX_MS` from each answer; a step that only ever held ends `unreachable`. Nothing is refused for lateness, so each step has its own ten minutes however long the one before it took, and a tell is never refused for age. One due time orders the runner: a first attempt is due at its turn and a retry at its last answer plus its gap (`dueAt`), and `nextEffect` over the runnable steps takes the one due first, so neither a stream of new runs nor a row of dead plugs starves the other. When a set lands, every older open set of that switch ends refused (`outdatedSets`, logged with the reason `NEWER_SET`); a toggle never ends a toggle, and the switch and nature are read from the body the landed fire fired with. After a restart `recovered` judges each step by its nature, read from the fire's own body: a claimed `sends` or `nudges` step ends `no_answer`, a claimed `sets` step resumes inside its time and ends `timeout` past it, a step between attempts resumes, and a step that never began an attempt forgets its start; a stored start ahead of the clock is clamped on every judgment. `readFire` reads the shape 8.14.84 stored until its dated removal, and an unreadable fire is dropped with one `uncertain` row. A tell with holes is filled through the read slot and can overlap an effect from another fire. Within one fire, `advance` reaches a tell only after the preceding step ends. A tell the pump withdrew while its fill ran is not put back. A text whose fill throws, a tell's or an effect's, is used with its holes marked and logged `uncertain` (`fillerOf`). An IFTTT key that is gone or cannot be read is a refusal at once, a post with no response is `no_answer`, and only a vault that cannot answer yet is a hold. `device_set` goes through the device road with `AUTOMATION_ATTEMPT_MS` as its bound, where a bound that passes in the device queue is a hold, a plug that never accepts a connection within `KASA_CONNECT_MS` is `unreachable` for every caller, and one that passes after the command was written is `no_answer`; the effect latch alone says whether a command went out, and no effect starts with `EFFECT_FLOOR_MS` of its bound left. `ifttt_trigger` goes through the assistant's IFTTT client with the same bound, its vault read counted, and an attempt whose bound is spent when the read returns is a hold; it needs its grant and so runs only at the home. An action whose switch this Gateway lacks is an error, failed at its turn. `stop()` starts no run after it, waits out the one in flight and lands what it ran. A runner that throws logs its error's class and a fixed reason, never the message, which could hold a URL.
- **Admission:** at most 64 fires wait (`admit`). A newer fire takes the place of an automation's unstarted one only when that one was stored by an earlier pass, logged `suppressed` once; an event's fire is never replaced, since each carries its own event. When the queue is full, the automation holding the most fires gives one up: one only waiting to tell on a full outbox, else an unstarted one, else any that is not live, oldest first. On a tie the newcomer's automation pays, with its own oldest unclaimed fire, or the newcomer itself when it holds no other, so a fire is refused, and logged, only when no automation holds more than its own would. A run is started once its `active` list is not empty, read from that alone, and a started run is never evicted, so one busy automation cannot refuse another's fire. One run per automation is started at a time (`mayRun`), at most `WAITING_EVENTS_MAX` event fires of one automation wait, and a newcomer past that is logged `suppressed` (`BEHIND`) with its tell still told while there is room.

- **Previews:** `automation_preview` is one request over the draft's trigger (an event's newest match, or a clock's names now): a text with holes comes back filled or with the hole a save would refuse, and a `condition` comes back true or false right now, or why not: it reads a value the run sets first (named in `runNames`), it does not read as true or false, or it cannot be read now. A condition a save would refuse answers that issue and its span.
- **Text with holes:** a tell's `message` and IFTTT's three values are texts that may hold `{expression}` holes in the console's language (`docs/console-live.md`). A hole reads the trigger's names (`value`, `device`, `measure` and `threshold` for a crossing; `value` and `field` for a value trigger; `event`, a record of the event's fields with its id and title, and `source` for an event) and every entity a host session reads, bar a slow member. Inside a function's step it also reads the function's declared values by name, each filled from the trigger or from the value the running automation set. A text whose hole cannot be read is an error, answered with its step, the parameter and the span: one left open, one that does not parse or holds two statements, a name that is neither the trigger's nor an entity, an entity named bare anywhere in it, an entity's member it lacks or its method left uncalled, a function or a method no value takes, a function given the wrong number of arguments, and a slow member. What a hole's value prints as is the preview's to show, since the check reads no value. The fire records the names as they stood (a crossing's number in the owner's unit, with the form the app shows), and the run fills each text from them.
- **Telling:** a tell is a step. It is told at its turn, in written order, as its own outbox event under its step's path, and wakes the lane; a tell after an effect waits for that effect, and two tells are two events. A message with a hole is filled first, through the read slot. With no room it waits, and ends `timeout` when its automation's window passes. The lane itself tells an event automation's leading tells with no message, through a pointer into its function's first steps, so it decides a wake only from those. A run whose every step is its automation's own tell is light: all such runs advance in one pass, none counts in the waiting cap, and they are the first to go when the queue is full. The event carries the trigger's fields (`field` and `value`, `time`, or an event's names that have a text form) and `message`. A tell that does not fit makes room by share (`roomFor` in `automationOutbox.ts`): it drops the oldest quiet event of the automation holding the most quiet events, the asker's own entry counted, never one that tells `now`, and each automation that lost events gets one `suppressed` row. Only an outbox full of `now` events holds the tell, logged refused once, until a clear makes room. A message with a hole is told with a `note` beside it, the owner's text as written, since what a hole filled may be third-party text: the assistant reads `note` as the owner's words and `message` as data. `told` clips the title and each field to the lane reader's bounds and the outbox's reader hides an entry outside them. A standing refusal is logged once per automation, action and step while it stands, compared with the last row of that action and step that is not a lost run (`logged` in `automationLog.ts`). A lost run (replaced, dropped for room, refused for a full queue: `LOST_RUNS`) is compared with that automation's latest row of any action, so it is logged again once a run came between.

- **The log** (`automationLog.ts`): at most `LOG_MAX` (64) rows across every automation, kept in the automation state with what stands. A row holds its kind (`step`, `tell`, `lost`, `trigger`), the automation, the fire's `seq` and time, an outcome and a fixed reason; a `step` row also names its path, its action or statement kind and the function it ran in. The kind is the row's key: a refusal logs once until another row of its key lands, and a lost run once until any other row of its automation lands, kept as state (`standing`), never read off the last row. A tell step held for a full outbox logs under its own step. Past the cap the automation holding the most rows loses its oldest (`capped`), so a busy function costs no other automation its rows. A gone automation's rows and standing are dropped at the next write of the state, or they would never be the largest holder and never leave.
- **The last run** (`automationLastRun.ts`): each automation's row carries `lastRun`, every step its last run reached (path, kind, outcome and reason, the side an `if` took, the case a `switch` took, the function), the step in flight and whether it still runs. Each step also says when its turn began and ended, in milliseconds from the run's start (`startMs`, `endMs`), stamped by the pass that first saw each (its window start for the first), whether an open step is retrying after a failed attempt and when an attempt first failed (`retriedMs`); no new stamp of a run is earlier than its latest, so a clock set back reorders nothing, and a run recorded before steps were timed stays untimed. It is kept after the run ends until the next run starts. It carries a stamp of what it ran, and is shown only while the automation's body (but for `enabled`) and each function the run entered are still that version, so an edit hides it and a toggle does not. Nothing records a save, an edit, a sweep or a carry of an automation or a function; the store keeps only each record's revision.
- **A run by hand** (`automation_run`, an automation id and a call id): one fire of its own, keyed by the call id so a repeat runs nothing again, its names what the trigger gives now (an event gives none, so its holes read unread), with no cool-down and replacing no waiting fire. Refused when the automation is gone, off or invalid, when an event automation is away from the home, or when admission turns it away.

- **Confirming a dangerous action:** `ifttt_trigger` is dangerous. An owner put whose dangerous actions are not all on the held record is refused with `confirm`, the labels to ask about, unless the op says `confirmed`.

- **A crossing's band:** the store hands computed fields one derived field per crossing automation (`crossing:<id>`, a one-sided band over the device's reading). It is evaluated and kept in the field state like a stored field, counts toward no cap and is listed nowhere, and an edit to the automation gives it a new basis, so the number it is saved over is its baseline. `drain()` reads it as `becomes` low or high. The row's sentence is the device's name, the reading's label, the direction and the threshold in the owner's unit, and its event tells the number it fired on.

- **One writer:** `write(intent)` is the only door into the store. `judgeAutomationWrite` in `automationJudge.ts` reads the intent against what is held and answers the rows to write or a refusal, and `createOwnerRecords.batch` commits them in one write, so a failed or refused set leaves the store as it was. The intents: `owner_put` and `owner_remove` (an event automation only at the assistant's home), `save` (an automation with its function, see Functions), `sweep` (functions no automation runs), `carry` (the home's whole set of event automations and the functions they run: one this Gateway cannot run is stored as it is and reads invalid, so a move loses nothing the owner wrote, and a set that does not fit under the cap or takes an id another automation holds is refused whole) and `conversion` (one sensor's stored thresholds rewritten as crossings, until 2027-01-15; `docs/devices.md`). The cap, the id shape, the revision and validity are the record store's, on every row.
- **One reader:** `drain()` is the only place a `value` transition becomes a fire. It runs at construction, after a put, a remove and a clear, and on each field commit. Repeating it changes nothing.
- **Checkpoint:** per automation, the record revision, incarnation, field epoch and `handledSeq`. A revision change (create, edit, re-enable) baselines at the field's current `seq`; an epoch change at that epoch's seq 0. A baseline whose write failed is held in memory for the next drain.
- **Crossing:** a stored transition above `handledSeq` with `value === becomes && previous !== becomes`. Transitions lost past the 16 kept log one `uncertain` run. Cool-down reads the transition's own time. Off the assistant's home a tell, and an action whose row says `home`, logs `refused`; its other actions run. An invalid or disabled automation never fires.
- **The outbox:** at most 256 events or 64 KiB. An event carries its tell's `when`, absent for `quietly`, and an older entry without one reads as `quietly`. Its id is its fire's member key, which starts with its automation's id (`ownerOf` reads it back) and is digested past 256 characters, and its `at` is its append time, strictly increasing. An event body this build cannot read stays held and unlisted. Entries leave by `clear`, which pumps again, so a repeated clear retries; with their automation, when an owner write removes it (an edit, a disable or a toggle keeps them); when the assistant lets go of this Gateway; and seven days after they were appended (`retained`), checked where the outbox is listed and at a restart as well as when a new entry asks for room.
- **The source:** the `sensors` source, labelled "Automations" (text fields automation, field, value, message and note), lists the outbox for the source lane. Its events say how they tell, so no event automation triggers on them.
- **Composition order:** read the home, build computed fields, build automations (it drains at construction, so it must see the home), then `start()`.

## Device definitions

`src/shared/device-definitions/`: one JSON file per model under its family, the same bytes whether shipped, built or shared. A definition is `{ format, key, version, family, label, models, match { sources, namePrefix, activeScan }, inputs, readings, examples, attribution }`: each input is a company's maker data as bytes, each reading a field spec and a node table over the inputs. `definitionRefusal` is the one load rule: the schema, sources inside the family's catalogued markers (a definition never widens the radio filter), every reading checked against its inputs, and every example replayed. `SHIPPED_DEFINITIONS` loads at boot and refuses a bad file. `govee-h5110` is the first.

## Newer kinds on an older phone

`scripts/codegen-kotlin.ts` gives every sealed root a decode policy in `SEALED_ROOTS`. A `preserve` root (`AssistantFieldSpec`, `ConsoleDeviceReadResult`) decodes a kind this build does not know to `Unknown(kind, raw)`; every `when` over it carries a fail-closed arm that shows the field and never saves or acts on it. Codegen refuses a discriminated root with no policy, and a `preserve` root without a future-kind fixture in `tests/fixtures/protocol/_manifest.json` (`expect: { ts: "fail", kotlin: "unknown" }`).
