# Fields, computed fields and automations

The Gateway reads typed values (a sensor's temperature, a frame of bytes), derives new ones from them, and tells the assistant when one becomes a value the owner named. None of it reaches the phone as code: the phone reads the declarations and the values.

## The field table

`src/shared/field-types.ts` holds the kinds and their rules once; codegen writes the same data into `Protocol.kt` as `FieldTypes`, and `kotlin-gate.sh` diffs it.

- **Kinds:** `enumeration` (Choice), `text`, `number`, `bytes`. Choice and text take condition tests; number and bytes take none, and `conditionsIssue` refuses a condition over them.
- **Units:** a number is stored in a stored unit (`C`, `%`); `F` is a display unit only. `toDisplay` and `fromDisplay` convert, a converted value storing at 0.01 so it reads back as typed.
- **Range:** `inRange` keeps `|value| x 10^decimals` within 2^53, so both runtimes format it the same.
- **Bytes:** lower-case hex, at most 64 bytes, shown as offset rows of eight (`bytesText`).
- **Parse and render:** `parseFieldValue` in `src/shared/field-values.ts` answers a value or an issue (`path`, `message`, `code`), rounding a reading to its declared decimals. `formatFieldValue` is the one text renderer; `FieldRules.kt` is its phone twin.
- **Pinned:** `tests/fixtures/field-types/vectors.json` (grammar, rounding, conversion, range, rendering), replayed by both runtimes.

## Owner records

`src/gateway/ownerRecords.ts`, `createOwnerRecords`: the store under computed fields and automations. Phone-minted ids, Gateway-named revisions, buried ids, `commitChecked`, `onChanged` after the write. `batch` plans several puts and removes against one draft and lands them in one write, or none when any is refused. The envelope (`id`, `revision`, `incarnation`, `kind`) parses strictly; a body this build cannot read is held unread, reserves its id and its place in the cap, and is written back untouched. A put carries its base revision, and a repeat of the stored content answers stored. The `refusal` hook runs on every put and on `invalidOf`, so validity is read, never stored; a refusal may carry the issue shape. A put marked `unfit` lands past it, for a record that arrives with the assistant. `refusalOf` plans a batch and answers its refusal without writing.

## Expressions

`src/shared/expressions.ts`. A flat node table, each node naming only earlier nodes: field, literal, compare, all, any, not, choose, band, take, arithmetic, unknown. At most 64 nodes.

- **Check:** `checkExpression` types every node against the inputs' declarations and refuses with an issue naming the node. All-text-literal branches infer a Choice of those literals.
- **Evaluate:** `evaluate` never throws. Whole-number arithmetic runs on BigInt and truncates toward zero; a result past 2^53, a division by zero or a short frame answers unknown. A band keeps its side, by node index, until a value passes its dead zone.
- **Values:** known or unknown with a reason. `conforms` reads a known value off its declared type as unknown.

## Computed fields

`src/gateway/computed/computedFields.ts`, `createComputedFields`. A computed field is a label, an optional unit and decimals, and a node table. Fields may name fields, as a DAG at most four deep.

- **One input port:** `input(ref)` answers a field's declaration and value together. Each pass reads every input once and resolves one snapshot of types, order and validity, which `typeOf`, `invalidOf` and `value` read.
- **State:** per field, a basis hash (expression plus every input's type), an `epoch` minted per fresh baseline, the last known value, `seq`, the band sides and the last 16 transitions (`previous`, `value`, `at`), all in one commit. An expression edit or a type change starts a new epoch and tells nothing; the first known value is a baseline. An unknown result reads unknown and keeps the last known value for the next comparison.
- **Calls:** `start()` runs the first pass once listeners are wired; `inputsChanged(keys)` re-evaluates fields naming those keys and their dependents; `typesChanged()` re-evaluates everything. `onCommit` fires after every landed write.

## Automations

`src/gateway/computed/automations.ts`, `createAutomations`, over the record in `src/shared/schemasAutomation.ts`. An automation is `enabled`, a trigger, a list of actions, and an optional `label` that replaces the row's sentence. A trigger is `event` (a source and its conditions, decided in the assistant's lane; `docs/assistant.md`), `value` (a Choice or boolean computed field, the value it `becomes`, and `coolDownSec`) `crossing` (a sensor's number: `device`, `measure`, `direction` above or below, `threshold`, `deadZone`, `coolDownSec`), `time` (a local `time` on its `weekdays` in a recorded `zone`) or `interval` (`everyMin`, counted from the slot it last handled). An automation holds one to eight actions, each a row of `AUTOMATION_ACTIONS` in `schemasAutomation.ts`: `tell_assistant` with `when` `now` or `quietly` and an optional `message`, `device_set` (a switch this Gateway holds and a verb) and `ifttt_trigger` (an event and up to three values). A sensor's thresholds write `crossing` automations that tell quietly, one per side that is set.

- **The action catalogue:** a row is the action's label, where it runs, `danger`, `home` (it does nothing away from the assistant's home) and its `params` in the order an editor draws them. A parameter is a name, a label and a kind: `text` (prose that may hold holes, with a `max`), `word` (letters, digits, `-` and `_`), `switch` (one of this Gateway's switches) or `choice` (one of its `options`). `automation-actions.test.ts` holds each row to its action's schema, and `holeTexts` finds an action's texts by its row. The listing serves the rows whole in `serves.actions`, so an editor draws an action from what its Gateway says and needs no build of its own for a new kind.
- **Clocks:** `automationClock.ts` names a time or interval trigger's next slot, `nextOccurrence` for a time and plain minutes for an interval. The state holds each clock's last slot handled; a clock that is saved, edited or switched back on starts from that moment, so it never fires for a slot before it. `tick()` fires each slot that has come round, tells the slot's clock time as `time`, and logs slots more than five minutes late as one `uncertain` run without firing them. One timer waits for the nearest slot, armed from the `now` the walk used, and the Gateway's persist tick walks again in case a timer was lost. A row answers `nextRunAt`. Neither kind moves with the assistant's home.
- **Fires:** a trigger that fires records a fire in the same commit as its checkpoint or slot: the automation, its incarnation and revision, a member key, the trigger's names, the fields it tells and its tell. An event trigger's fire is recorded by the lane once the poll that saw the event has committed, once per member (`memberKey`), so later activity on a thread fires again. `pump` in `automations.ts` is the one reader. It retires a fire whose automation is gone, was edited or cannot run here. For effects (every action that is not a tell) it writes the fire as claimed, runs each in order (`runEffect` in `automationRunner.ts`, which never throws) and logs each run with its action kind as `ran`, `refused` or `uncertain`; a claim with no run left logs `uncertain` and never runs again. It then fills a message's holes and queues the tell. At most 64 fires wait; past that a fire waiting only on the outbox gives up its place, else the new one is refused and logged. `device_set` goes through the device road's assistant surface, `ifttt_trigger` through the assistant's IFTTT client, which needs its grant and so runs only at the home. An action whose switch this Gateway lacks makes the automation invalid. `stop()` starts no run after it and waits out the one in flight.
- **Text with holes:** a tell's `message` and IFTTT's three values are texts that may hold `{expression}` holes in the console's language (`docs/console-live.md`). A hole reads the trigger's names (`value`, `device`, `measure` and `threshold` for a crossing; `value` and `field` for a value trigger; `event`, a record of the event's fields with its id and title, and `source` for an event) and every entity a host session reads, bar a slow member. A put refuses a text whose hole cannot be read, answering `hole` with the action's index, the parameter and the span: one left open, one that does not parse or holds two statements, a name that is neither the trigger's nor an entity, an entity named alone, an entity's member it lacks or its method left uncalled, a function or a method no value takes, and a slow member. What a hole's value prints as is the preview's to show, since the check reads no value. The fire records the names as they stood (a crossing's number in the owner's unit, with the form the app shows), and the run fills each text from them.
- **Telling:** a tell is queued by `pump`, in the write that retires its fire, and wakes the lane. A message with no hole is ready when the trigger fires; one with a hole is filled first. An event automation's tell with a message is told this way too, as its own outbox event beside the source's own, so the lane decides a wake only from tells with no message. The event carries the trigger's fields (`field` and `value`, `time`, or an event's names that have a text form) and `message`. A full outbox holds the tell, logged refused once, until a clear makes room; its effects have already run. `told` clips the title and each field to the lane reader's bounds and `outbox.events()` hides an entry outside them. A refusal that stands (not the home, a full outbox) is logged once per automation.
- **Confirming a dangerous action:** `ifttt_trigger` is dangerous. An owner put whose dangerous actions are not all on the held record is refused with `confirm`, the labels to ask about, unless the op says `confirmed`.

- **A crossing's band:** the store hands computed fields one derived field per crossing automation (`crossing:<id>`, a one-sided band over the device's reading). It is evaluated and kept in the field state like a stored field, counts toward no cap and is listed nowhere, and an edit to the automation gives it a new basis, so the number it is saved over is its baseline. `drain()` reads it as `becomes` low or high. The row's sentence is the device's name, the reading's label, the direction and the threshold in the owner's unit, and its event tells the number it fired on.

- **One writer:** `write(intent)` is the only door into the store. `judgeAutomationWrite` in `automationJudge.ts` reads the intent against what is held and answers the rows to write or a refusal, and `createOwnerRecords.batch` commits them in one write, so a failed or refused set leaves the store as it was. The intents: `owner_put` and `owner_remove` (no alert id, and an event automation only at the assistant's home), `carry` (the home's whole set of event automations: one this Gateway cannot run is stored as it is and reads invalid, so a move loses nothing the owner wrote, and a set that does not fit under the cap or takes an id another automation holds is refused whole), `adoption` (stored rules, until 2026-11-28) and `projection` (one sensor's whole alert set, under that sensor's id prefix only). The cap, the id shape, the revision and validity are the record store's, on every row.
- **One reader:** `drain()` is the only place a `value` transition becomes a fire. It runs at construction, after a put, a remove and a clear, and on each field commit. Repeating it changes nothing.
- **Checkpoint:** per automation, the record revision, incarnation, field epoch and `handledSeq`. A revision change (create, edit, re-enable) baselines at the field's current `seq`; an epoch change at that epoch's seq 0. A baseline whose write failed is held in memory for the next drain.
- **Crossing:** a stored transition above `handledSeq` with `value === becomes && previous !== becomes`. Transitions lost past the 16 kept log one `uncertain` run. Cool-down reads the transition's own time. Off the assistant's home, a crossing logs `refused`. An invalid or disabled automation never fires.
- **The outbox:** at most 256 events or 64 KiB. An event carries its tell's `when`, absent for `quietly`, and an older entry without one reads as `quietly`. Its id is its fire's member key, digested past 256 characters, and its `at` is its append time, strictly increasing. An event body this build cannot read stays held and unlisted. Entries leave by `clear`, which pumps again, so a repeated clear retries.
- **The source:** the `sensors` source, labelled "Automations" (text fields automation, field, value and message), lists the outbox for the source lane. Its events say how they tell, so no event automation triggers on them.
- **Composition order:** read the home, build computed fields, build automations (it drains at construction, so it must see the home), then `start()`.

## Device definitions

`src/shared/device-definitions/`: one JSON file per model under its family, the same bytes whether shipped, built or shared. A definition is `{ format, key, version, family, label, models, match { sources, namePrefix, activeScan }, inputs, readings, examples, attribution }`: each input is a company's maker data as bytes, each reading a field spec and a node table over the inputs. `definitionRefusal` is the one load rule: the schema, sources inside the family's catalogued markers (a definition never widens the radio filter), every reading checked against its inputs, and every example replayed. `SHIPPED_DEFINITIONS` loads at boot and refuses a bad file. `govee-h5110` is the first.

## Newer kinds on an older phone

`scripts/codegen-kotlin.ts` gives every sealed root a decode policy in `SEALED_ROOTS`. A `preserve` root (`AssistantFieldSpec`, `ConsoleDeviceReadResult`) decodes a kind this build does not know to `Unknown(kind, raw)`; every `when` over it carries a fail-closed arm that shows the field and never saves or acts on it. Codegen refuses a discriminated root with no policy, and a `preserve` root without a future-kind fixture in `tests/fixtures/protocol/_manifest.json` (`expect: { ts: "fail", kotlin: "unknown" }`).
