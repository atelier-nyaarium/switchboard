# Fields, computed fields and automations

The Gateway reads typed values (a sensor's temperature, a frame of bytes), derives new ones from them, and tells the assistant when one becomes a value the owner named. None of it reaches the phone as code: the phone reads the declarations and the values.

## The field table

`src/shared/field-types.ts` holds the kinds and their rules once; codegen writes the same data into `Protocol.kt` as `FieldTypes`, and `kotlin-gate.sh` diffs it.

- **Kinds:** `enumeration` (Choice), `text`, `number`, `bytes`. Choice and text take condition tests; number and bytes take none, and `conditionsIssue` refuses a condition over them.
- **Units:** a number is stored in a stored unit (`C`, `%`); `F` is a display unit only. `toDisplay` and `fromDisplay` convert, a converted value storing at 0.01 so it reads back as typed.
- **Range:** `inRange` keeps `|value| x 10^decimals` within 2^53, so both runtimes format it the same.
- **Bytes:** lower-case hex, at most 64 bytes, shown as offset rows of eight (`bytesText`).
- **Parse and render:** `parseFieldValue` in `src/shared/field-values.ts` answers a value or an issue (`path`, `message`, `code`), rounding a reading to its declared decimals. `formatFieldValue` is the one text renderer; `FieldRules.kt` is its phone twin.
- **Pinned:** `tests/fixtures/field-types/vectors.json` (grammar, rounding, conversion, range, rendering), replayed by both runtimes.

## Owner records

`src/gateway/ownerRecords.ts`, `createOwnerRecords`: the store under computed fields and automations. Phone-minted ids, Gateway-named revisions, buried ids, `commitChecked`, `onChanged` after the write. `batch` plans several puts and removes against one draft and lands them in one write, or none when any is refused. The envelope (`id`, `revision`, `incarnation`, `kind`) parses strictly; a body this build cannot read is held unread, reserves its id and its place in the cap, and is written back untouched. A put carries its base revision, and a repeat of the stored content answers stored. The `refusal` hook runs on every put and on `invalidOf`, so validity is read, never stored; a refusal may carry the issue shape. A put marked `unfit` lands past it, for a record that arrives with the assistant. `refusalOf` plans a batch and answers its refusal without writing. A refusal carries an `OwnerCause` (`bad_id`, `invalid`, `newer_build`, `moved`, `spent`, `absent`, `removed`, `unsaved`, or a `cap` naming the total or a kind), so no caller guesses a code from prose, and `batch` checks `maxByKind` and the total against the batch's final row count, whatever order it lists its writes in. `unreadOf` says whether a newer build's row holds an id.

## Expressions

`src/shared/expressions.ts`. A flat node table, each node naming only earlier nodes: field, literal, compare, all, any, not, choose, band, take, arithmetic, unknown. At most 64 nodes.

- **Check:** `checkExpression` types every node against the inputs' declarations and refuses with an issue naming the node. All-text-literal branches infer a Choice of those literals.
- **Evaluate:** `evaluate` never throws. Whole-number arithmetic runs on BigInt and truncates toward zero; a result past 2^53, a division by zero or a short frame answers unknown. A band keeps its side, by node index, until a value passes its dead zone.
- **Values:** known or unknown with a reason. `conforms` reads a known value off its declared type as unknown.

## Computed fields

`src/gateway/computed/computedFields.ts`, `createComputedFields`. A computed field is a label, an optional unit and decimals, and a node table. Fields may name fields, as a DAG at most four deep.

- **One input port:** `input(ref)` answers a field's declaration and value together. Each pass reads every input once and resolves one snapshot of types, order and validity, which `typeOf`, `invalidOf` and `value` read.
- **State:** per field, a basis hash (expression plus every input's type), an `epoch` minted per fresh baseline, the last known value, `seq`, the band sides and the last 16 transitions (`previous`, `value`, `at`), all in one commit. An expression edit or a type change starts a new epoch and tells nothing; the first known value is a baseline. An unknown result reads unknown and keeps the last known value for the next comparison.
- **Calls:** `start()` runs the first pass once listeners are wired; `inputsChanged(keys)` re-evaluates fields naming those keys and their dependents; `typesChanged()` re-evaluates everything. `onCommit` fires after every landed write.

## Automations

`src/gateway/computed/automations.ts`, `createAutomations`, over the record in `src/shared/schemasAutomation.ts`. An automation is `enabled`, a trigger, a list of actions, and an optional `label` that replaces the row's sentence. A trigger is `event` (a source and its conditions, decided in the assistant's lane; `docs/assistant.md`), `value` (a Choice or boolean computed field, the value it `becomes`, and `coolDownSec`) `crossing` (a sensor's number: `device`, `measure`, `direction` above or below, `threshold`, `deadZone`, `coolDownSec`), `time` (a local `time` on its `weekdays` in a recorded `zone`) or `interval` (`everyMin`, counted from the slot it last handled). An automation holds one to eight actions, each a row of `AUTOMATION_ACTIONS` in `schemasAutomation.ts`: `tell_assistant` with `when` `now` or `quietly` and an optional `message`, `device_set` (a switch this Gateway holds and a verb) and `ifttt_trigger` (an event and up to three values). A threshold on a sensor is a `crossing` the owner writes.

- **The action catalogue:** a row is the action's label, where it runs, `danger`, `home` (away from the assistant's home it is refused unsent and an editor does not offer it) and its `params` in the order an editor draws them. A parameter is a name, a label and a kind: `text` (prose that may hold holes, with a `max`), `word` (letters, digits, `-` and `_`), `switch` (one of this Gateway's switches) or `choice` (one of its `options`). `automation-actions.test.ts` holds each row to its action's schema, and `holeTexts` finds an action's texts by its row. The listing serves the rows whole in `serves.actions`, so an editor draws an action from what its Gateway says and needs no build of its own for a new kind.
- **The trigger catalogue:** `AUTOMATION_TRIGGERS` holds one row per trigger kind with the names a text's hole may use and a short description of each (`event` and `source` for an event; `value`, `device`, `measure` and `threshold` for a crossing; `time` for a clock). `AUTOMATION_TRIGGER_NAMES` is derived from it, so the save's hole check, the fill and the preview read one table, and a test holds each row's names to what a real fire fills. The listing serves the rows in `serves.triggers`, so an editor lists a trigger's names before the trigger is complete.
- **Functions:** a function is an owner record beside the automations (`src/shared/schemasFunction.ts`): a name, up to `FUNCTION_PARAMS_MAX` values typed `device`, `text` or `number`, and a tree of steps. A `do` step runs an action, its arguments literals or expressions read at the step's start. At most `FUNCTIONS_MAX` exist and 64 records in all, one id space spans both kinds, and a function a newer build wrote is held unread, counted in the caps, and its automation reads `FUNCTION_UNREAD` and never fires. An automation runs one through the `run_function` pointer (`function`, literal `values`, `keepTryingMin`, `coolDownSec`), which is never an effect and so has no runner; `FUNCTION_STEP_KINDS` is held against the action kinds and validity's step table is built from it.
- **The tree:** a step is `do`, `if` (`when`, `steps`, `else`), `try` (`steps`, `catch`), `exit`, `throw` (`text`), `let` (`name`, `value`), `wait` (`minutes`) or `note`. A list holds at most `FUNCTION_STEPS_MAX` steps, a body `FUNCTION_STEPS_TOTAL_MAX` in all, nested `FUNCTION_DEPTH_MAX` deep.
  - **A step's path** is numbers alone, owned by `automation-walk.ts`: `0.2.0.1` is the call at action 0, its step 2, that step's first side, step 1. A first side (an if's then, a try's body) is 0, the second (else, catch) is 1.
  - **How a frame moves** is `moved` in `automationFrames.ts`, pinned by `tests/fixtures/automation-frames/failure-table.json`: a failed step is remembered and the next runs; inside a try it jumps to the catch with the failure as `e`; a `throw` unwinds to the nearest try or ends the frame; `exit` ends it quietly. A frame that ends with a failure nothing caught ends its call refused.
  - **At its turn** an `if` takes the side its condition holds and fails `unread`, taking neither, when the condition is not true or false. A `let` keeps a JSON value in the frame's `vars` (`FRAME_VARS_MAX` of them, each within `FRAME_VAR_BYTES_MAX` bytes). A `wait` stores when it ends and the run goes on at the first pass after it, a restart included; a waiting run is started, so no newer fire evicts it.
  - **Scope** for a step: the trigger's names, the function's values, the frame's variables, and `e` inside a catch (`code`, `message`, printing its message).
  - **A set after a wait** is dated by the wait's end (`intentAt`), so it does not lose to another automation's set that landed while it waited.
  - **Save checks** are one entry per kind in validity's `STEPS`, read at every depth through `stepsOf`. A refusal names its step by those numbers in `step`, with `param` and, for a hole, `start` and `end`.
- **Fit:** `src/shared/automation-fit.ts` says whether a trigger and a pointer's values fill what a function takes. `AUTOMATION_TRIGGER_GIVES` is the one table of what each trigger kind gives by name and type, `EVENT_GIVEN_FIELDS` (`id`, `title`, `url`) beside a source's declared fields is what an event gives, and the fire reads the same table. `triggerGiven`, `fitOf` and `functionReads` answer fit, hidden (another source's event) and the names still to set. A crossing's `device` is the sensor's name and gives text, so it never fills a device value. `tests/fixtures/automation-fit/vectors.json` is replayed by `assistant/FunctionFit.kt`.
- **The save op:** `automation_save` (`schemasAutomationSave.ts`) is a value op carrying the automation, its base, an optional function as `edit` (an id and base) or `copy` (a `from` and its base), and `confirmed`. The judge lands the automation and its function in one batch or refuses with a code from `AUTOMATION_SAVE_REFUSALS` and its facts (`moved`, `gone`, `full` with `max` and `kind`, `invalid`, `hole` with the record, path, param and span, `unfit` with the automations that stop fitting, `unknown_function`, `newer_function`, `cool_down_twice`, `confirm` with labels, `no_key`, `no_free_id` and the rest), never by prose. An edit of a shared function is refused `unfit` only for what it brings. A save that only points may name `functionBase`, the function's revision as the editor showed it, and is refused `moved` when the stored one differs. `automation_check` carries the same payload, writes nothing, and answers `ready` or the refusal a save would get now, with the `reads` of the body it would run; it shares one assessment with the save (`assess`), so the two cannot disagree on the same rows, and it reserves nothing. A copy takes the id `copyIdOf` names, claimed by `claimDerived` so a rerun reaches it and nothing is written over; the key is in `automation-function-key`, never logged or answered. A new event-triggered automation that reaches more than a tell, and an edit that gives a function's users new reach, answer `confirm`.
- **The walk:** `reached` in `automation-walk.ts` answers what an automation does in written order as closed entries: an `action` (never a call), a `step` of a function a call was followed into, or an `unfollowedCall` with its reason (`not-expanded` without a function lookup, `missing` when the function is not held). `visit` reads an entry and needs a handler for every case and step kind. An unfollowed call proves nothing about what it reaches, so the confirmation rule counts no reach for it. The walk also encodes and decodes the dotted step path (`siteOf`, `byPath`). The phone's twin answers the same entries, pinned by `tests/fixtures/automation-walk/vectors.json`.

- **One assessment of a body, a policy per boundary:** `argsIssue` checks an action's values, flat or a step's (a hole only in a text parameter, a device value against the offered switches, a choice against its options, literal values against the action's row). `assessBody` yields every issue in written order (`trigger`, `action`, `step`, `call`, `fit`). A read takes all of them, so a carried function written unfit, a switch that went, or `FUNCTION_LEFT` (its function did not come with a move, read off the trigger) reads invalid and does not arm. An automation's write stops on all but `fit` and a step's own detail; a function row's write on its first step issue; a fire about to start on the automation's own issues; frame entry on `step` and `fit`, so a call into a function that went unsound is refused before any of its steps runs; and a step's read values pass the same check before its effect. A save that points an automation at another function than it ran is refused `invalid` when that stored function fails its own step check; an unchanged pointer and a toggle are not. `automation_put` and the list row answer an older phone as before.
- **The list answers functions:** `functions` holds an `AutomationFunctionRow` (id, revision, body, `users` in list order, `moves` when its users move with the home, `reads`, `invalid`) built in `listing()` from one store read; a function with no user is unlisted, `usersOf` answers unknown while an unread automation row is held, and the delete at none and the sweep read that. `serves.functions` states the cap, the step kinds and the value types.
- **A call's frames:** a fire that enters a function holds a `frames` record by call path with the function, incarnation and revision it pinned, and the body pinned in `functionVersions` by `frameKey` (`commit` is the one writer, `pinnedFunctions`). The call step is replaced by the function's steps under dotted paths (`enter`); a function gone or unread at entry ends the call refused (`FUNCTION_GONE`, `FUNCTION_UNREAD`), and each step reads its values once at its turn into `frame.resolved`, ending refused with `VALUE_UNREAD`, `STEP_UNFIT` or `FRAME_UNREAD` rather than throwing. A function's tell is a step told through the outbox under `stepMember`. `keepTryingMin` is each step's window under the call and `coolDownSec` is the automation's cool-down only where the trigger has none, measured from admission (`firedAt` by automation and incarnation) and logging one `COOLING` row until a run comes between.
- **The retire rule:** `retireOf` decides in order: the automation gone or another incarnation; `enabled: false` (`SWITCHED_OFF`); no pinned body; a started run, which continues on the body and frame it pinned; an unstarted fire at another revision; then the automation's own issues, its function left to frame entry. An edit therefore retires only an unstarted fire, and a function's revision change never retires one. A newer set landed on a switch ends an older open set of it even inside a function that has not resolved yet, the newest landed set per switch held in `landedSets`.
- **The carry:** a move takes functions by value (`CarriedFunction`, chosen by `carriedFunctionsOf` in `automation-carry.ts`, vectors under `tests/fixtures/automation-carry`). At the destination `judgeCarry` gives a function its own id unless an automation holds it or a staying automation runs it, then `carryIdOf`, the same on a rerun; pointers follow, and one whose function did not come never binds to a stayer's. A move in place claims the function a held event automation here already runs at its own id (`inPlace`) and, when it is held, leaves it as it stands. A let-go deletes no function: one with no user is tracked in `unusedFunctions` and swept after `FUNCTION_UNUSED_KEEP_MS` on the persist tick through the `sweep` intent, never while an unread row is held. A carry from an older phone (`functions` null) lands a pointer unfit only when its function is not held at the destination, so a move back binds to the function the let-go kept.
- **Clocks:** `automationClock.ts` names a time or interval trigger's next slot, `nextOccurrence` for a time and plain minutes for an interval. The state holds each clock's last slot handled; a clock that is saved, edited or switched back on starts from that moment, so it never fires for a slot before it. `tick()` fires each slot that has come round, tells the slot's clock time as `time`, and logs slots more than five minutes late as one `uncertain` run without firing them. One timer waits for the nearest slot, armed from the `now` the walk used, and the Gateway's persist tick walks again in case a timer was lost. A stored slot more than five minutes ahead of the clock means the clock went back: that automation's walk starts again from now and passes over the one slot it had last handled (`skip`), logging one `suppressed` row when it does, so a step back of any size refires nothing. A row answers `nextRunAt`. Neither kind moves with the assistant's home.
- **Fires:** a trigger that fires records a fire in the same commit as its checkpoint or slot: the automation, its incarnation and revision, a member key, the trigger's names, the fields it tells, its tell, and one record per step keyed by step path, with the step whose turn it is in `active`. An event trigger's fire is recorded by the lane once the poll that saw the event has committed, once per member (`memberKey`), so later activity on a thread fires again. `pump` in `automations.ts` is the one reader, driven by the pure rules in `automationFires.ts` (`nextEffect`, `nextFill`, `claim`, `admit`, `mayRun`, `outdatedSets`) and in `automationSteps.ts` (`dueAt`, `heard`, `recovered`, `retries`). The state also holds each automation body a held fire fired with, by `versionKey`, in `versions`, whose one writer is `commit`; `bodyOf` and `stepAt` answer every question about a step after the fire (its nature, the kind on its log row, the switch a landed set names, the runner and the tell's text), so an edit of the automation changes none of them. It retires a fire whose automation is gone, was edited or cannot run here; `settle` decides that (`retireOf`) before recovery and before answers land, so a retiring fire is never resumed or retried, its steps are judged with no nature, and a retiring fire ends every step it began with what is known: a claim ends `no_answer`, an open step with a last word ends with it (`endHeard`, through `timedOut`) and logs its row, a step that never heard one logs nothing, then one retire row covers the steps left unreached, none for a finished fire. Each effect (every action that is not a tell) is a step. A fire's steps run in written order, one effect in flight across every fire, each claimed in its own write before it runs (`runEffect` in `automationRunner.ts`, which never throws), and a failed step is logged and the next runs. An attempt answers `done`, `refused`, `unreachable` or `no_answer`, or is a hold, which is no attempt: nothing was sent (the vault cannot be read yet, the devices are not loaded, the device road did not start it by its deadline, or a throw before the send). A step ends logged with its action kind as `ran`, `refused` or `uncertain`. `attemptOf` in `automationActions.ts` maps the road's `Outcome` to a word (a driver failure through `FAILURE_WORDS`, a refusal as `refused`), and an effect the latch marks unknown is `no_answer`. `KIND_NATURES` and `VERB_NATURES` beside `RUNNERS` give each effect `sets` (on, off), `sends` (an IFTTT post) or `nudges` (a toggle), and `RETRIED` in `automationSteps.ts` is the one table of nature against word: `sets` retry `unreachable` and `no_answer`, `sends` retry `unreachable`, `nudges` retry nothing, and `refused` ends every nature. A step keeps trying for `KEEP_TRYING_MS` from its own turn, backing off `BACKOFF_MIN_MS` to `BACKOFF_MAX_MS` from each answer; a step that only ever held ends `unreachable`. Nothing is refused for lateness, so each step has its own ten minutes however long the one before it took, and a tell is never refused for age. One due time orders the runner: a first attempt is due at its turn and a retry at its last answer plus its gap (`dueAt`), and `nextEffect` over the runnable steps takes the one due first, so neither a stream of new runs nor a row of dead plugs starves the other. When a set lands, every older open set of that switch ends refused (`outdatedSets`, logged with the reason `NEWER_SET`); a toggle never ends a toggle, and the switch and nature are read from the body the landed fire fired with. After a restart `recovered` judges each step by its nature, read from the fire's own body: a claimed `sends` or `nudges` step ends `no_answer`, a claimed `sets` step resumes inside its time and ends `timeout` past it, a step between attempts resumes, and a step that never began an attempt forgets its start; a stored start ahead of the clock is clamped on every judgment. `readFire` reads the shape 8.14.84 stored until its dated removal, and an unreadable fire is dropped with one `uncertain` row. A fill runs beside the effect in flight, so a tell never waits behind an effect; a tell the pump withdrew while its fill ran is not put back. A text whose fill throws, a tell's or an effect's, is used with its holes marked and logged `uncertain` (`fillerOf`). An IFTTT key that is gone or cannot be read is a refusal at once, a post with no response is `no_answer`, and only a vault that cannot answer yet is a hold. `device_set` goes through the device road with `AUTOMATION_ATTEMPT_MS` as its bound, where a bound that passes in the device queue is a hold, a plug that never accepts a connection within `KASA_CONNECT_MS` is `unreachable` for every caller, and one that passes after the command was written is `no_answer`; the effect latch alone says whether a command went out, and no effect starts with `EFFECT_FLOOR_MS` of its bound left. `ifttt_trigger` goes through the assistant's IFTTT client with the same bound, its vault read counted, and an attempt whose bound is spent when the read returns is a hold; it needs its grant and so runs only at the home. An action whose switch this Gateway lacks makes the automation invalid. `stop()` starts no run after it, waits out the one in flight and lands what it ran. A runner that throws logs its error's class and a fixed reason, never the message, which could hold a URL.
- **Admission:** at most 64 fires wait (`admit`). A newer fire takes the place of an automation's unstarted one only when that one was stored by an earlier pass, logged `suppressed` once; an event's fire is never replaced, since each carries its own event. When the queue is full, the automation holding the most fires gives one up: one only waiting to tell on a full outbox, else an unstarted one, else any that is not live, oldest first. On a tie the newcomer's automation pays, with its own oldest unclaimed fire, or the newcomer itself when it holds no other, so a fire is refused, and logged, only when no automation holds more than its own would. A run is started once its `active` list is not empty, read from that alone, and a started run is never evicted, so one busy automation cannot refuse another's fire. One run per automation is started at a time (`mayRun`), at most `WAITING_EVENTS_MAX` event fires of one automation wait, and a newcomer past that is logged `suppressed` (`BEHIND`) with its tell still told while there is room.

- **Text with holes:** a tell's `message` and IFTTT's three values are texts that may hold `{expression}` holes in the console's language (`docs/console-live.md`). A hole reads the trigger's names (`value`, `device`, `measure` and `threshold` for a crossing; `value` and `field` for a value trigger; `event`, a record of the event's fields with its id and title, and `source` for an event) and every entity a host session reads, bar a slow member. Inside a function's step it also reads the function's declared values by name, each filled from the trigger or from the value the running automation set. A put refuses a text whose hole cannot be read, answering `hole` with the action's index, the parameter and the span: one left open, one that does not parse or holds two statements, a name that is neither the trigger's nor an entity, an entity named bare anywhere in it, an entity's member it lacks or its method left uncalled, a function or a method no value takes, a function given the wrong number of arguments, and a slow member. What a hole's value prints as is the preview's to show, since the check reads no value. The fire records the names as they stood (a crossing's number in the owner's unit, with the form the app shows), and the run fills each text from them.
- **Telling:** a tell is queued by `pump` as soon as it is ready, and wakes the lane. A message with no hole is ready when the trigger fires; one with a hole is filled first. An event automation's tell with a message is told this way too, as its own outbox event beside the source's own, so the lane decides a wake only from tells with no message. The event carries the trigger's fields (`field` and `value`, `time`, or an event's names that have a text form) and `message`. A tell that does not fit makes room by share (`roomFor` in `automationOutbox.ts`): it drops the oldest quiet event of the automation holding the most quiet events, the asker's own entry counted, never one that tells `now`, and each automation that lost events gets one `suppressed` row. Only an outbox full of `now` events holds the tell, logged refused once, until a clear makes room. A message with a hole is told with a `note` beside it, the owner's text as written, since what a hole filled may be third-party text: the assistant reads `note` as the owner's words and `message` as data. `told` clips the title and each field to the lane reader's bounds and the outbox's reader hides an entry outside them. A standing refusal is logged once per automation, action and step while it stands, compared with the last row of that action and step that is not a lost run (`logged` in `automationLog.ts`). A lost run (replaced, dropped for room, refused for a full queue: `LOST_RUNS`) is compared with that automation's latest row of any action, so it is logged again once a run came between.

- **The run log** (`automationLog.ts`): at most `LOG_MAX` (64) rows across every automation, kept in the automation state. A row holds the automation, the fire's `seq` and time, an outcome, a fixed reason, the action kind and, for a step, its path (`step`) and the function it ran in (`function`); a call refused at entry names the call's path and its function. A tell step held for a full outbox logs under its own step, so its refusal is logged again once that step's own row came between. Past the cap the automation holding the most rows loses its oldest (`capped`), so a busy function costs no other automation its rows. A row whose automation is no longer held is dropped at the next write of the state (`pruned`), or it would never be the largest holder and never leave. Nothing records a save, an edit, a sweep or a carry of an automation or a function; the store keeps only each record's revision.

- **Confirming a dangerous action:** `ifttt_trigger` is dangerous. An owner put whose dangerous actions are not all on the held record is refused with `confirm`, the labels to ask about, unless the op says `confirmed`.

- **A crossing's band:** the store hands computed fields one derived field per crossing automation (`crossing:<id>`, a one-sided band over the device's reading). It is evaluated and kept in the field state like a stored field, counts toward no cap and is listed nowhere, and an edit to the automation gives it a new basis, so the number it is saved over is its baseline. `drain()` reads it as `becomes` low or high. The row's sentence is the device's name, the reading's label, the direction and the threshold in the owner's unit, and its event tells the number it fired on.

- **One writer:** `write(intent)` is the only door into the store. `judgeAutomationWrite` in `automationJudge.ts` reads the intent against what is held and answers the rows to write or a refusal, and `createOwnerRecords.batch` commits them in one write, so a failed or refused set leaves the store as it was. The intents: `owner_put` and `owner_remove` (an event automation only at the assistant's home), `save` (an automation with its function, see Functions), `sweep` (functions no automation runs), `carry` (the home's whole set of event automations and the functions they run: one this Gateway cannot run is stored as it is and reads invalid, so a move loses nothing the owner wrote, and a set that does not fit under the cap or takes an id another automation holds is refused whole), `adoption` (stored rules, until 2026-11-28) and `conversion` (one sensor's stored thresholds rewritten as crossings, until 2027-01-15; `docs/devices.md`). The cap, the id shape, the revision and validity are the record store's, on every row.
- **One reader:** `drain()` is the only place a `value` transition becomes a fire. It runs at construction, after a put, a remove and a clear, and on each field commit. Repeating it changes nothing.
- **Checkpoint:** per automation, the record revision, incarnation, field epoch and `handledSeq`. A revision change (create, edit, re-enable) baselines at the field's current `seq`; an epoch change at that epoch's seq 0. A baseline whose write failed is held in memory for the next drain.
- **Crossing:** a stored transition above `handledSeq` with `value === becomes && previous !== becomes`. Transitions lost past the 16 kept log one `uncertain` run. Cool-down reads the transition's own time. Off the assistant's home a tell, and an action whose row says `home`, logs `refused`; its other actions run. An invalid or disabled automation never fires.
- **The outbox:** at most 256 events or 64 KiB. An event carries its tell's `when`, absent for `quietly`, and an older entry without one reads as `quietly`. Its id is its fire's member key, which starts with its automation's id (`ownerOf` reads it back) and is digested past 256 characters, and its `at` is its append time, strictly increasing. An event body this build cannot read stays held and unlisted. Entries leave by `clear`, which pumps again, so a repeated clear retries; with their automation, when an owner write removes it (an edit, a disable or a toggle keeps them); when the assistant lets go of this Gateway; and seven days after they were appended (`retained`), checked where the outbox is listed and at a restart as well as when a new entry asks for room.
- **The source:** the `sensors` source, labelled "Automations" (text fields automation, field, value, message and note), lists the outbox for the source lane. Its events say how they tell, so no event automation triggers on them.
- **Composition order:** read the home, build computed fields, build automations (it drains at construction, so it must see the home), then `start()`.

## Device definitions

`src/shared/device-definitions/`: one JSON file per model under its family, the same bytes whether shipped, built or shared. A definition is `{ format, key, version, family, label, models, match { sources, namePrefix, activeScan }, inputs, readings, examples, attribution }`: each input is a company's maker data as bytes, each reading a field spec and a node table over the inputs. `definitionRefusal` is the one load rule: the schema, sources inside the family's catalogued markers (a definition never widens the radio filter), every reading checked against its inputs, and every example replayed. `SHIPPED_DEFINITIONS` loads at boot and refuses a bad file. `govee-h5110` is the first.

## Newer kinds on an older phone

`scripts/codegen-kotlin.ts` gives every sealed root a decode policy in `SEALED_ROOTS`. A `preserve` root (`AssistantFieldSpec`, `ConsoleDeviceReadResult`) decodes a kind this build does not know to `Unknown(kind, raw)`; every `when` over it carries a fail-closed arm that shows the field and never saves or acts on it. Codegen refuses a discriminated root with no policy, and a `preserve` root without a future-kind fixture in `tests/fixtures/protocol/_manifest.json` (`expect: { ts: "fail", kotlin: "unknown" }`).
