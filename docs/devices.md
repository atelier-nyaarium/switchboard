# Devices

The Gateway controls the owner's smart plugs on the local network with no cloud in the loop. One generic layer holds the records and the actions; a brand driver speaks the plug's protocol. Kasa is the first driver.

## The record

`src/shared/schemasDevices.ts`. A device is `{ id, name, kind, driver, address, revision }`. The id is the plug's MAC in lower-case colon form, the one spelling `normalizeDeviceMac` answers. A name may not normalize to a MAC, so a name can never resolve as another device's id; `deviceNameRefusal` is the one name rule, called by the schema and by the store. The kind is `switch` with the verbs `on`, `off` and `toggle`, or `sensor`, which only reads. `DRIVER_KINDS` names the one kind each driver serves, and `deviceRefusal` holds the kind rules: a switch's address is an IPv4 literal and a scan refreshes it; a sensor's address is its own MAC, it names the radio that listens for it (`radio: gateway | phones`), and it may name the definition that reads it (`definition`).

## The store

`src/gateway/devices/store.ts`, on `openDurable` and `commitChecked`, the sole writer, Gateway-named revisions. Restore refuses the file whole on a duplicate id, an unnormalized MAC, a driver that does not serve the record's kind, or a record ahead of the list's revision. A row this build cannot read (a newer kind or field) is held raw behind its `{ id, revision }` envelope: it reserves its id and its place in the cap, stays out of `list` and `get`, refuses edits, and is written back on every commit; a corrupt envelope still refuses the file. A removed id leaves a tombstone holding its last revision, bounded to the newest 256, so a re-added plug continues its numbering. A repeated add of the same address and name, a repeated removal at the tombstone's revision, and a rename to the held name at the previous revision are lost answers.

## The driver contract

`src/gateway/devices/driver.ts`. A switch's driver takes an operation context: the ambient clock, an abort signal and an effect latch. `identify` returns the MAC an address reports; `read`, `set`, `rename`, `schedule` (read, put) and `settings` (read, put) take a record. A failure is typed: `unreachable` or `timeout` with a detail and, when the transport knows, `sent`; `refused` with the plug's `err_code` and its message; `invalid` with a detail; `wrong_device` when the address reports another MAC, which points the owner at a scan. Any failure after a step landed carries `landed`: `done` of `total` steps.

**A sensor has no driver I/O:** `SensorReads` answers its held readings, and the road refuses it a switch's ops (`not_supported`); a rename is the record's alone. `src/gateway/devices/sensorReadings.ts` reads the bound definition's template over the last advert heard, with each measure's 24-hour low and high from `readingsHold.ts`, and answers each reading as a computed field input (`device:<mac>/<key>`) whose basis names the definition version, so a version bump starts a new baseline. A `device_read` of a sensor answers the `sensor` discriminator (readings, `heardAt`, `stale`), so an older phone decodes it as Unknown.

**Pairing a sensor:** `device_add` with a `radio` pairs on what was heard (`sightings`), with no identify: the advert must name a catalogued sensor family (`familyOf` in `src/shared/ble-recognition.ts`), and a named definition must belong to that family and match the advert. A device of the family with no definition pairs unread. `docs/fields.md` holds the definition format.

**Readings and thresholds:** The daemon listens for the `gateway`-radio sensors named in `device_watch` and sends their adverts back. Only frames from the current host socket are ingested. A phone posts readings for a `phones`-radio sensor with `device_reading_post`. Both paths call `road.ingest` outside the per-device queue and without a lease. `readingsHold.ts` keeps distinct payloads in memory and 24 hourly low and high buckets. The buckets flush on the tick, and computed fields receive every reading key. A sensor unheard for 15 minutes reads stale. `sensor_threshold_put` stores each measure's threshold in `sensor-thresholds.json` at that record's revision. The band field and one automation per side derive from the stored threshold through `src/gateway/computed/thresholds.ts`. The Gateway rebuilds these projections at startup and retries failed writes on the persist tick. A sensor read returns stored thresholds. Removing a sensor drops its thresholds. A fresh pairing with the same MAC clears leftovers from a failed removal, and a repeated add preserves thresholds. The scan relay reports whether the host has a Bluetooth radio in `device_list` and the scan answer. A `gateway`-radio sensor add without a radio answers `no_radio`.

**Identity before every mutation.** The driver reads `sysinfo`, compares the MAC with the record id and sends nothing on a mismatch, so a reused DHCP address cannot switch the wrong plug. Each mutation opens an attempt on the context's effect latch after the identity passes and before it is written, and denies only that attempt when the plug refuses the command or the transport never wrote it. The latch stays marked while any attempt is undenied, so a later step's refusal cannot hide an earlier step that landed.

## The Kasa driver

`src/gateway/devices/kasa/`. The legacy XOR protocol over TCP 9999: a four-byte length and the autokey from 0xAB (`codec.ts`); one connection per command, closed by the transport itself at the deadline, answers capped at 64 KiB (`transport.ts`). `kasaDriver.ts` covers `get_sysinfo`, `set_relay_state`, `set_dev_alias`, `set_led_off`, the `time` module, the `schedule` module and `cnCloud`. A schedule put carries the schedule its edit began over. The Gateway reads the plug in the same queue turn and refuses `stale` when it differs, since the record revision does not move when the Kasa app edits a rule. It then reconciles against `get_rules` by rule id, matches an id-less rule by content so a replay adds nothing, leaves any rule it cannot represent alone, and reads back; a failure after a step landed carries how many landed (`schedule.ts`). The cloud disconnect unbinds and points the server at a non-cloud value, noting when only the first step landed (`cloud.ts`). A plug on KLAP firmware does not speak this protocol and is not served.

## The road

`src/gateway/devices/road.ts`. Every handler, console or assistant, goes through `createDeviceRoad`, which owns the store, the drivers, the leases, the per-device queue, the close fence, the toggle doubt and the one failure map. A console operation is bound at `CONSOLE_ANSWER_WAIT_MS - CONSOLE_HOP_MARGIN_MS` and an assistant one at `ASSISTANT_WAITS.action`; a listing reads each plug and a scan identifies each moved candidate under a nested bound of its own, and close drains every lease. A turn on a device's queue is raced at its start against the lease, so a turn that never starts answers not started while a started one runs to completion. The deadline gates starting an effect, never committing one that landed: a plug answer that arrives late still commits.

A handler receives a `Slot` (the record, the store's writes for that id, `drive`, `attempt` for compensation, `identify`, `expect`) or a `Plug` (a held record and its driver), and declines through one `Declined` value that `shapes.ts` projects into each wire shape. `src/gateway/compose/composeDevices.ts` holds only the handler bodies, which `device-road-residue.test.ts` enforces.

**The toggle doubt.** A toggle whose relay command may have landed without confirmation is remembered per device, and the next toggle is refused until a read, a listing or an explicit on or off confirms the state, or the device is removed. A refusal from the plug, or a command that was never written, records no doubt.

## Answers

Each console op is declared once in `schemasDevices.ts`: its request is the `ConsoleOp` member (`DEVICE_CONSOLE_REQUESTS`) and its result sits beside it in `DEVICE_CONSOLE_RESULTS`, which the compiler holds to one per request. The console handler routes every device op through `isDeviceConsoleOp` to the stage's one `DeviceConsole` function.

Every result is `{ kind: "ok", ... }` or `{ kind: "refused", refusal }`, generated into Kotlin as a sealed class. A refusal carries a closed `code`, an `effect` (`none` when the plug cannot have changed, `unknown` when it may have), how many steps `landed` when a multi-step write was cut short, a bounded `detail`, and the held `record` when the refusal concerns one. A never-started op answers `timeout` with effect `none`. A reader decides from the code and the effect and never parses the detail. A read answers its settings only when their own read succeeded, so one failed settings call cannot hide a relay state and schedule already read. `tests/fixtures/protocol/` holds device requests and results both runtimes replay.

## The scan

`src/mcp/devcontainer/kasaScan.ts` in the host daemon, behind the closed `kasaScan` host op: no caller input, the legacy discovery payload broadcast on every non-loopback IPv4 interface's broadcast address, a four-second window under the host bound, datagrams over 4 KiB dropped before decrypting, a stop after 1024, typed candidates capped at the device limit. One failed send does not end a scan; every send failing does. `src/gateway/devices/scan.ts` relays it and answers a daemon that is down or late as `daemon_away` or `timeout`, never as an empty list. The Gateway's scan handler then identifies each moved paired candidate at its new address before refreshing the record, and a scan whose later refreshes miss the deadline still answers its candidates.

**Bluetooth in the daemon:** `src/mcp/devcontainer/bluetooth/` speaks D-Bus to BlueZ over the system bus socket (`dbusWire.ts`, `dbusClient.ts`). `createBluezCoordinator` in `bluez.ts` keeps the discovery holds callers want and one link per connection epoch: down, up (adapter, powered, the device cache, discovery off, on or unknown, the applied filter) or closed. One reconcile loop is the only code that calls BlueZ: it connects, sets the union of the holds' filters, starts discovery, and stops it once the last hold is released. Events (a `bluetoothd` restart, the adapter going, a power change) only edit the link and mark it dirty; a failure retries on one backoff timer, reset only after a stable window on the same epoch. The `bleScan` host op holds discovery for one bounded window, seeded from the cache, and answers `no_radio` on a host with no adapter. The watch (`deviceWatch.ts`) keeps one hold for the `gateway`-radio sensors the Gateway names and sends their adverts back in batches.

## The assistant

The assistant's `device` tool is the console's op table, each op offered or withheld (`DEVICE_TOOL_OFFERS` in `src/shared/schemasDeviceTool.ts`): list, read, set, rename, schedule put and setting put are offered; scan, home network, add and remove are withheld. The tool's input is the discriminated union of the console's own request objects for the offered kinds, so a console op added without an entry there does not compile, and offering one takes that entry and its result schema in `DEVICE_TOOL_RESULTS`. Its `device_list` answers every record with live state and the catalogue's capabilities, reading each plug under its own bound so one silent plug cannot time out the answer; the other ops run the console's handler bodies on the assistant surface. The assistant's answers are the console's parsed through the assistant schemas (`assistantShape`), which drop a record's address; a failure is a fixed phrase per kind, never the plug's or the transport's text, since a socket error names an address, so the assistant sees `err_code` and never the message. A failure after a step landed tells it how many landed and that the last command's outcome is unknown. A setting put that matches a danger act's `put` in the catalogue (`dangerActOf`) waits on the owner's card (`actGuard.runDevice`), which carries the act's own consent words, and the assistant surface itself refuses that put without `approved`, so no other caller can skip the card. The tool rides `/assistant/run` as a `{ device, callId }` body (`deviceDispatch.ts`), so a retry joins by call id; `docs/assistant.md` holds the road.

## Deploying

The daemon ships the scan op, the plugin the actions, the Gateway the store and the road. Readers first: `./start-host-daemon.sh`, then the plugin build and the assistant's MCP restart, then the Gateway, then the phone, whose device pages read and send the console ops together. The Router needs nothing, since a device op rides `gateway_value` sealed.

## The phone

`DeviceOps.kt` holds every device operation and lands each answer through a typed slot (`DeviceSlots.kt`) over `PublishedViews` (`SlotViews.kt`): the list, the scan, a plug's write claim, and per plug its live state, schedule part (with the owner's edit and the schedule it began over) and settings part. A per-plug slot is owned only while the plug is listed at the incarnation its ticket was minted for, so a late answer for a removed or re-added plug lands nothing. A Gateway the roster does not name is asked nothing, and the workspace's re-provision generation is shared. `DeviceRules.kt` holds what the pages decide. `AssistantIntegrationsPage` and `AssistantDevicePage` only draw and call. `SandboxDevices.kt` answers as a Gateway in the emulator build.

## The catalogue

Every brand, service and protocol is declared once, in `src/shared/schemasIntegrations.ts`: its group (protocol, service, brand, which is also the Add page's order), label, blurb, how it is discovered (`scan`, `listen`, `none`), what it needs (fields, today one `secret` kind), what it yields (devices or actions), the device capabilities it supports (`switch`, `schedule`, `led`, `clock`, `cloud`) and its acts, each with a tier (`act` or `danger`). `scripts/codegen-kotlin.ts` generates `IntegrationRegistry.kt` from it as Kotlin enums and a list, so a group, a discovery mode, a need kind or a capability the phone has no renderer for fails to compile rather than drawing an empty section. Device drivers and the grant-bearing service ids derive from the catalogue; a driver with no entry does not compile.

A brand may declare its Bluetooth markers (`bluetooth`: service ids, maker data with a prefix and an optional companion service, and the names and data that rule a device out). `familyOf` recognizes a family by those markers, never a model by its name; `BleRecognition.kt` is its phone twin, pinned by `tests/fixtures/ble-recognition/vectors.json`.

The Gateway answers `offered`, the catalogue ids it serves, on the assistant state; a `listen` entry is left out until the phone has its Add flow. The phone draws Add from the compiled catalogue filtered by that answer, so an older Gateway hides an entry rather than showing a dead page, and an older phone ignores the field.

On the phone, `IntegrationRules.kt` holds the decisions: the offered entries, the Add page's groups and search, when a service counts as added (it holds a grant), a device row's brand line and its trouble line (shown only while the switch cannot say the state), its power control (`powerSlot`: a switch once the state is known, a spinner before the first read, nothing while the plug cannot say), the capabilities and acts of a record's brand, and the settings index's counts per type. `IntegrationAddPage` is the catalogue; `IntegrationEntryPage` is one entry, decided by its discovery: a scan entry has New device (when the entry declares a setup) and Scan side by side, then one list: found plugs with Add, then paired rows that open the device page, and a service entry is a form of its needs, granting a secret from the vault, with Remove once added. The device page draws its brand's section one renderer per declared capability, and an act by its tier: a danger act is red and confirms.

## Setting up a fresh device

A fresh or reset Kasa plug leaves the home network and broadcasts its own open setup network, which the Gateway's scan cannot reach and Sakura, being on WiFi alone, cannot join. The phone does the hand-off, since it is near the device. A catalogue entry declares `setup`: its kind (`access_point`), the prefix its setup network names start with, and what it needs (the home WiFi password, a `secret`).

`PlugSetupOps` runs it. Android's own network picker (`WifiNetworkSpecifier` with an SSID prefix) lists the matching setup networks and the owner picks one, so joining needs no scan and no location permission, only `CHANGE_NETWORK_STATE`; the main WiFi stays connected. Over that network the phone reads `get_sysinfo` (the MAC, the model) and `get_scaninfo` (the networks the plug sees, with no signal). Signal bars come from the phone's own scan, which needs precise location granted and switched on (`phoneLocation`, the Location row on the Features page). The phone asks for a fresh scan as it joins, and `phoneSignals` keeps the strongest 2.4 GHz result under two minutes old for each listed network. With none heard, the list is radios in the plug's order. The owner names it, and the phone sends `set_dev_alias` and `netif.set_stainfo` through `KasaCodec`, the twin of the Gateway's codec pinned by `tests/fixtures/kasa-codec/vectors.json`. Your WiFi is the network the Gateway's host is on, which the plug must join for the Gateway to reach it: `device_home_network` relays the daemon's closed `wifiNetwork` host op, which reads `nmcli`, then `iwgetid`, then `netsh.exe` under WSL, and answers `none` when the host is on no WiFi. The phone asks before it joins the plug's network, falls back to the network the last setup used, and only then asks the owner to pick; the page says only whether the plug can see your WiFi. Picking a network closes the list. The password is a two-way choice, Type password or Vault, starting on Vault when a past setup used an entry; a vault entry opens through the usual approval and, when it cannot be read, the choice flips to Type password. A typed password is used once and kept nowhere. Set up stays disabled until the name, the network and the password or entry are all set (`setupReady`). The phone then asks the Gateway to scan every few seconds: a plug found there is added under its new name, or re-matched if it was already paired. One that has not joined within the wait asks for the password again, and the retry picks the setup network again and refuses a different plug. A plug set up this way was never added to a Kasa account. `SandboxPlugSetup` is the emulator's plug, whose first hand-off does not take.
